QA Assessment
02 / 08

The brief, and what shipped

Automate two flows against the Shiftbase demo environment: signup + onboarding up to the dashboard, and login. This is what came back.

🎯

Both flows, end to end

Signup walks the 8-step questionnaire and setup wizard to the dashboard; login handles the MFA interstitial. Interactions read as intent through the Steps API — no raw selectors in any test.

🔍

Eleven defects found

Not the point of the brief, but the honest by-product of testing a real product: three found while building, eight from a dedicated adversarial pass. Zero were false positives.

📼

Evidence, not claims

Every defect carries a reproduction and screen recording / screenshot. Findings that could not be pinned by a portable test are reported with the reason, not faked into one.

▶️

Runnable by anyone

npm ci && npm test on a clean clone with no .env. Verified by cloning fresh; the suite mints its own account through the real signup flow.

The defects

Eleven confirmed, zero refuted. The headline is one UI testing alone would never reach.

HIGH · compliance

Terms & Data-Processing-Agreement acceptance is enforced only in the browser

POST /api/signup accepts a payload with accept_conditions: false and creates a fully usable account — the required consent checkbox has no server-side counterpart. Reproduced from two fresh sessions, each followed by a successful login. Reported, not automated: a test would replay a compliance-bypass exploit on every CI run against a shared environment.

How the findings were trusted

Every adversarial finding was reproduced, then handed to a second, independent check whose only job was to disprove it.

1

Probe

Drive genuinely new ground — API gate bypass, injection, boundaries, rate limiting, timing. Reproduce twice before recording.

→
2

Refute

A separate verifier tries to kill each finding: not reproducible, already-known, expected behaviour, or a sandbox artifact. Default to refuted when unsure.

→
3

Keep what survives

8 of 8 survived; 3 had their severity corrected. The corrections are the proof the refutation was real, not a rubber stamp.

  • ✓

    Selectors that survive copy changes

    The questionnaire's radio inputs are unclickable (sr-only); options are targeted by stable formcontrolname + value, not the visible label — which disagrees with the value (“Scheduler” is Planner).

  • ✓

    App bugs reported, never worked around

    When the app misbehaved, the test was left describing correct behaviour and the bug was written up — not adjusted to match.

QA Assessment
07 / 08

Engineering choices worth a look

The decisions a reviewer running this cold would notice.

🔑

No committed credentials

A setup project mints an account via the real signup flow when no .env is present, so a cold clone runs green. Secrets live in .env (gitignored); an independent sweep confirmed none leaked.

🔁

Flake, root-caused not retried

The Angular questionnaire drops clicks mid-render; every input is now re-applied until it lands (verified 12× with retries off). The residual is the app's own gateway flakiness, left to configured retries.

👁️

Watchable headed runs

npm run test:headed drops to one worker and paces each action, so a reviewer can actually follow the flows instead of windows racing.

🔒

TLS reality documented

The demo serves a private-CA cert that rolls every 24h; the suite sets ignoreHTTPSErrors and says so plainly — on production that setting would hide a real defect.
